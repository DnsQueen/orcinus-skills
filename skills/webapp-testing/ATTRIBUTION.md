- **Upstream bug found and fixed in the bundled copy (2026-11-06, from an external review):** `scripts/with_server.py` had four defects. (1) The server's stdout and stderr were piped but never read, so a log-heavy server blocked on the full pipe and its output was swallowed — the ORCINUS team hit this itself (the script once left a child server running and swallowed stdout). Fixed: both pipes are drained continuously in background threads and forwarded to this script's stdout/stderr. (2) Readiness was only "the port is open", which a different service on the same port can satisfy. Fixed: `--ready-path` (e.g. `/health`) does an HTTP GET and requires an HTTP response; while waiting, the script also checks that the server process is still alive. (3) Cleanup called `terminate()` on the shell process (`shell=True`), so the real server kept running. Fixed: each server starts in its own process group (`start_new_session=True` on POSIX) and cleanup signals the whole group (SIGTERM, then SIGKILL). (4) The test command had no timeout. Fixed: `--test-timeout` (default 300s). The fixes are covered by `scripts/test_with_server.py` (6 tests).
- **Upstream bugs found and fixed in the bundled copy (2026-11-07, round 6, S7 / 3-F2-01 / 3-F2-02 / 3-F2-03):** the round-5 readiness fix was only half true. (5) `_http_ready` returned True for ANY HTTP response, so a health endpoint answering 500 or 503 counted as ready — the docstring even described that as intended. Fixed: readiness requires a 2xx response by default, configurable with `--ready-status` (`2xx`, a range like `200-299`, or a list like `200,204`). (6) `--ready-path` was a single value passed to every server, although backend and frontend usually have different health paths. Fixed: `--ready-path` is repeatable, one path per server (a single value still applies to all); any other count is a usage error. (7) A different service already holding the port was declared ready even WITH `--ready-path`. Fixed: the port is checked free before the server starts — a held port is an error and the test command never runs against the wrong service. Residual, documented in the script: the check has a race (a service binding between the check and the start), and a wrong service answering 2xx on the ready path cannot be told apart from ours without a token. (8) Cleanup SIGTERMed the group and then waited for the LEADER only: when the leader died promptly, a SIGTERM-ignoring child survived — the SIGKILL half ran only on timeout. Fixed: after the leader's wait (either outcome) the group is verified empty and SIGKILLed if anything remains. Residual: pgid reuse in the milliseconds between the leader's exit and the check (only a container/cgroup or job object closes that hole). `shell=True` stays: the command comes from the script's own `--command`, operator-supplied, not untrusted input — upstream design, recorded as design debt (round 6, 2-S8), not an injection hole. Tests grew from 6 to 12.
- **Upstream bug found and fixed in the bundled copy (2026-11-07, round-6 follow-up, CI 0.9.5 Windows):** (9) On Windows, cleanup called `terminate()` on the shell process only — Windows has no process groups (`start_new_session` is POSIX-only) — so the real server kept listening after cleanup (normal flow and test-command timeout) and the next run on the same port was refused as "already in use" (ready-path repeatable and ready-path rejects a non-HTTP service). Fixed: cleanup kills the whole tree with `taskkill /PID <pid> /T /F` while the leader is still alive; a taskkill failure on a still-running server prints a warning instead of failing silently. Residual: no graceful phase on Windows — taskkill /F is a force kill (there is no SIGTERM equivalent for an arbitrary process tree); a graceful shutdown via CTRL_BREAK_EVENT would need the server started in a new process group and a console attached, and was not added. (10) The SIGTERM-ignoring-child test's server script used `preexec_fn` and the `sleep` binary, neither of which exists on Windows, so the server crashed at startup (`ValueError: preexec_fn is not supported on Windows platforms`). Fixed: on Windows the child is a Python sleeper (`sys.executable -c "import time; time.sleep(120)"`); it still survives a shell-only kill, so the test keeps its meaning. Tests grew from 13 to 16.
- **Scope note:** this skill tests local web applications with Playwright (Python) and needs a browser. Upstream says these skills are for demonstration/education and should be tested in the user's own environment before being relied on for critical work.
