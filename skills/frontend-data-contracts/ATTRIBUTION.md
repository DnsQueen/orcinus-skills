- **Integration finding (verified in the eval, not hidden):** the demo API — designed by `api-and-interface-design` — does not use one envelope. Its summary endpoint returns a bare payload (`{"total":80,...}`), while its list endpoint returns `{data:[...], pagination:{...}}`. This skill requires one envelope (`{data}` / `{error}`). The client built in the eval therefore has to handle both shapes, which is exactly the inconsistency the skill exists to prevent. Aligning the API to one envelope is a breaking change under `breaking-change` and belongs in a new API version, not in the client.
- **Scope, stated plainly:** the skill is written for React and React Native apps (fetch, Zod/Valibot, TanStack Query / RTK Query / SWR in the examples). Its rules — one client as the only fetch boundary, parse-don't-validate, one envelope, one normalized error, branded IDs — are framework-agnostic in principle, and the eval proves them against the demo API with a framework-free client. The demo API is a throwaway server in /tmp, not a real service.
- **Wiring:** the ORCINUS router loads this skill whenever code consumes an API — see the router's shared rules. It is the client side of the contract that `api-and-interface-design` designs and `breaking-change` guards.
