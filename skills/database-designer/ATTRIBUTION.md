- **Script audit (done before bundling):** all three scripts use only the Python standard library (`argparse`, `json`, `re`, `sys`, `collections`, `typing`, `dataclasses`, `hashlib`, `datetime`). No network calls, no database connections, no subprocess, no `eval`/`exec`, no credential handling. Each script writes only to the output file the user names with `-o`, and reads only the input files given. The scripts generate SQL text; they never execute it against a database — applying a migration is the user's step, not the script's.
- **Upstream bug found and fixed in the bundled copy:** `migration_generator.py` failed on *any* schema change with `Error: Object of type Column is not JSON serializable`. The changes dict stores raw `Column`/`Table` dataclass instances, and `_generate_migration_id` / `_calculate_changes_hash` call `json.dumps()` on that dict, which cannot serialize dataclasses — so the generator only worked when there were no changes at all. Fixed minimally in the bundled copy with a `_json_default` helper (serializes dataclasses with `asdict()`, raises for anything else), used at exactly the two `json.dumps(changes, ...)` calls. The fix is marked in the file. The other two scripts are untouched. The upstream bug was verified by running the unmodified script (v1 vs v1 works; any real change fails) and the fix by running the fixed script (the migration is generated).
- **Tool limitations found by the audit and the eval (not hidden):** (1) the `--format sql` output prints forward steps only — the rollback SQL exists only in the `--format json` output; the skill's rule that every migration needs a reversible counterpart must be satisfied from the JSON output or by hand. (2) The generated SQL does not add a FOREIGN KEY constraint: when the target schema adds an FK, the generator recreates the column (expand-contract dance) but emits no `FOREIGN KEY` / `REFERENCES` constraint, so the FK is not enforced after the migration. (3) The `DROP_OLD_COLUMN` step inside the zero-downtime dance is marked LOW risk, while a standalone `DROP COLUMN` is correctly HIGH — the tool's risk model does not flag the drop inside the dance. (4) `--validate-only` emits no validation queries for a `DROP COLUMN` step. (5) The rollback for a dropped column re-adds an empty column — it does not restore the data. The skill's own rules (take a logical backup before dropping a column with data; test the down migration in staging) must be applied by the agent, not relied on from the tool.
