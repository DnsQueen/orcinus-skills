- **Script audit (done before bundling):** all three scripts use only the Python standard library (`argparse`, `json`, `re`, `sys`, `collections`, `typing`, `dataclasses`, `hashlib`, `datetime`). No network calls, no database connections, no subprocess, no `eval`/`exec`, no credential handling. The scripts generate SQL text; they never execute it against a database — applying a migration is the user's step, not the script's.
- **Upstream bugs found and fixed in the bundled copy (2026-11-06, from external reviews):** (1) `migration_generator.py` failed on *any* schema change with `Error: Object of type Column is not JSON serializable`. The changes dict stores raw `Column`/`Table` dataclass instances, and `_generate_migration_id` / `_calculate_changes_hash` call `json.dumps()` on that dict, which cannot serialize dataclasses — so the generator only worked when there were no changes at all. Fixed minimally in the bundled copy with a `_json_default` helper (serializes dataclasses with `asdict()`, raises for anything else), used at exactly the two `json.dumps(changes, ...)` calls. The fix is marked in the file. (2) A unique-only, foreign-key-only or check-only column change produced an empty ALTER (`ALTER TABLE t\n    ;`) — invalid SQL that claimed to do the change and did nothing — because `_columns_different` detected those changes but `_modify_column_step` only converted type, nullable and default to SQL. Fixed: the step now emits the ADD/DROP CONSTRAINT statements for unique, foreign key and check, `_describe_column_changes` now describes check changes, and a detected change with no SQL handler raises instead of generating an empty ALTER. This also closes the eval's recorded FK gap (limitation 2 below): a foreign-key change now produces an ADD CONSTRAINT FOREIGN KEY step. (3) Constraints were added before the old ones were dropped, so a primary-key swap failed. Fixed: constraint removal now runs before constraint addition in `generate_migration`. (4) A table that was both renamed and column-changed lost its column changes, because `_compare_columns` only compares tables with the same name. Fixed: renamed tables now get their columns, constraints and indexes compared (under the old name, since the column and constraint steps run before the rename step), and the rename step records the similarity score and that it is a heuristic to confirm. (5) The zero-downtime path was labelled zero-downtime but had no write-synchronisation, no cutover and no backfill verification, the temp column carried only the data type (not the target's NOT NULL, UNIQUE, DEFAULT, CHECK or REFERENCES), and the DROP COLUMN step inherited the default LOW risk. Fixed: the temp column now carries the target's full definition, DROP_OLD_COLUMN is HIGH risk (RENAME is MEDIUM, COPY is MEDIUM), and the plan summary carries a `zero_downtime_warning` that the output is an expand-contract DRAFT requiring application coordination (dual-write during EXPAND, a backfill check before CONTRACT, a cutover) and must not be run automatically on real data. The other two scripts are untouched. The fixes are covered by `test_migration_generator.py` (17 tests).
- **Second review round (2026-11-06, also from external reviews):** (6) An index that kept its name but changed columns was invisible — `_compare_table_indexes` compared only the name set. Fixed: same-name indexes are compared by a normalised signature (columns in order, unique, predicate, method, expression); a changed one produces a DROP + ADD. Index removal now runs before index addition in `generate_migration`, so a same-name replacement does not fail with "index already exists". (7) A renamed table that also lost a column produced a DROP COLUMN against the old table name after the rename — the table no longer existed under that name. Fixed: dropped columns for a renamed table are recorded under the NEW name (the drop runs after the rename); addition, modification, constraints and indexes still use the old name (they run before the rename). (8) `_create_table_step` wrote a foreign key as `REFERENCES users.id` (invalid SQL) because it never used the existing `_references_sql` helper, and it dropped the table-level unique and check constraints and the per-column CHECK. Fixed: the FK now uses `_references_sql` (`users(id)`), and the step emits the column CHECK plus the table-level unique (`uq_table_col1_col2`) and check constraints. (9) `_add_column_step` built the column from type/NOT NULL/DEFAULT only and dropped the new column's UNIQUE, foreign key and CHECK. Fixed: it now uses `_column_definition_sql` (the full definition). (10) An index declared on a NEW table was silently lost: the CREATE TABLE step does not emit indexes and `_compare_indexes` only compared tables present in both schemas. Fixed: new tables' indexes are appended to `indexes_added`. Found by the SQLite integration tests. The round-2 fixes are covered by `test_migration_generator.py` (5 new tests) and `test_migration_integration.py` (5 tests that execute the migration on a real SQLite database, introspect the final schema with PRAGMA, compare it to the target, check the data survived, and run the rollback).
- **Lint (2026-11-06, second review round):** `ruff check --select E4,E7,E9,F` on the ORCINUS-owned Python found 7 pre-existing upstream style issues in `migration_generator.py` (4 unused imports, 3 f-strings without placeholders). Removed the unused imports and de-f-stringed the literals; behaviour unchanged, all 17 unit + 5 integration tests still pass. The drift manifest hash was updated for this file. The other two vendored scripts (`index_optimizer.py`, `schema_analyzer.py`) have the same class of upstream style issues but are pure vendored copies and are intentionally excluded from the ruff run (see `pyproject.toml`).
- **Dialect (declared, 2026-11-06):** the generator emits PostgreSQL-style SQL (`ALTER COLUMN ... TYPE`, `ADD/DROP CONSTRAINT`, `information_schema` validation queries). SQLite executes the overlapping subset (CREATE TABLE, ADD/DROP COLUMN, CREATE/DROP INDEX, RENAME TABLE, DROP TABLE), which is what the integration tests cover. Two SQLite gaps, found while writing those tests: SQLite rejects `ALTER TABLE ... ADD COLUMN ... UNIQUE` ("Cannot add a UNIQUE column" — for SQLite that needs a CREATE UNIQUE INDEX instead), and the `validation_sql` on each step uses `information_schema` (PostgreSQL), not SQLite's PRAGMA. The integration tests use PRAGMA as the SQLite equivalent.
- **Tool limitations found by the audit and the eval (not hidden):** (1) the `--format sql` output prints forward steps only — the rollback SQL exists only in the `--format json` output; the skill's rule that every migration needs a reversible counterpart must be satisfied from the JSON output or by hand. (2) ~~The generated SQL does not add a FOREIGN KEY constraint~~ — FIXED (see the fixes above). (3) ~~The `DROP_OLD_COLUMN` step inside the zero-downtime dance is marked LOW risk~~ — FIXED (it is HIGH now). (4) `--validate-only` emits no validation queries for a `DROP COLUMN` step. (5) The rollback for a dropped column re-adds an empty column — it does not restore the data. The skill's own rules (take a logical backup before dropping a column with data; test the down migration in staging) must be applied by the agent, not relied on from the tool.
