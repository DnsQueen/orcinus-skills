- **Upstream bugs found and fixed in the bundled copy (2026-11-06, from external reviews):** (1) `migration_generator.py` failed on *any* schema change with `Error: Object of type Column is not JSON serializable`. The changes dict stores raw `Column`/`Table` dataclass instances, and `_generate_migration_id` / `_calculate_changes_hash` call `json.dumps()` on that dict, which cannot serialize dataclasses — so the generator only worked when there were no changes at all. Fixed minimally in the bundled copy with a `_json_default` helper (serializes dataclasses with `asdict()`, raises for anything else), used at exactly the two `json.dumps(changes, ...)` calls. The fix is marked in the file. (2) A unique-only, foreign-key-only or check-only column change produced an empty ALTER (`ALTER TABLE t\n    ;`) — invalid SQL that claimed to do the change and did nothing — because `_columns_different` detected those changes but `_modify_column_step` only converted type, nullable and default to SQL. Fixed: the step now emits the ADD/DROP CONSTRAINT statements for unique, foreign key and check, `_describe_column_changes` now describes check changes, and a detected change with no SQL handler raises instead of generating an empty ALTER. This also closes the eval's recorded FK gap (limitation 2 below): a foreign-key change now produces an ADD CONSTRAINT FOREIGN KEY step. (3) Constraints were added before the old ones were dropped, so a primary-key swap failed. Fixed: constraint removal now runs before constraint addition in `generate_migration`. (4) A table that was both renamed and column-changed lost its column changes, because `_compare_columns` only compares tables with the same name. Fixed: renamed tables now get their columns, constraints and indexes compared (under the old name, since the column and constraint steps run before the rename step), and the rename step records the similarity score and that it is a heuristic to confirm. (5) The zero-downtime path was labelled zero-downtime but had no write-synchronisation, no cutover and no backfill verification, the temp column carried only the data type (not the target's NOT NULL, UNIQUE, DEFAULT, CHECK or REFERENCES), and the DROP COLUMN step inherited the default LOW risk. Fixed: the temp column now carries the target's full definition, DROP_OLD_COLUMN is HIGH risk (RENAME is MEDIUM, COPY is MEDIUM), and the plan summary carries a `zero_downtime_warning` that the output is an expand-contract DRAFT requiring application coordination (dual-write during EXPAND, a backfill check before CONTRACT, a cutover) and must not be run automatically on real data. The other two scripts are untouched. The fixes are covered by `test_migration_generator.py` (17 tests).
- **Second review round (2026-11-06, also from external reviews):** (6) An index that kept its name but changed columns was invisible — `_compare_table_indexes` compared only the name set. Fixed: same-name indexes are compared by a normalised signature (columns in order, unique, predicate, method, expression); a changed one produces a DROP + ADD. Index removal now runs before index addition in `generate_migration`, so a same-name replacement does not fail with "index already exists". (7) A renamed table that also lost a column produced a DROP COLUMN against the old table name after the rename — the table no longer existed under that name. Fixed: dropped columns for a renamed table are recorded under the NEW name (the drop runs after the rename); addition, modification, constraints and indexes still use the old name (they run before the rename). (8) `_create_table_step` wrote a foreign key as `REFERENCES users.id` (invalid SQL) because it never used the existing `_references_sql` helper, and it dropped the table-level unique and check constraints and the per-column CHECK. Fixed: the FK now uses `_references_sql` (`users(id)`), and the step emits the column CHECK plus the table-level unique (`uq_table_col1_col2`) and check constraints. (9) `_add_column_step` built the column from type/NOT NULL/DEFAULT only and dropped the new column's UNIQUE, foreign key and CHECK. Fixed: it now uses `_column_definition_sql` (the full definition). (10) An index declared on a NEW table was silently lost: the CREATE TABLE step does not emit indexes and `_compare_indexes` only compared tables present in both schemas. Fixed: new tables' indexes are appended to `indexes_added`. Found by the SQLite integration tests. The round-2 fixes are covered by `test_migration_generator.py` (5 new tests) and `test_migration_integration.py` (5 tests that execute the migration on a real SQLite database, introspect the final schema with PRAGMA, compare it to the target, check the data survived, and run the rollback).
- **Third review round (2026-11-06, also from external reviews):** (11) Falsy defaults were dropped: a default of `0` (or `""`) was lost in CREATE TABLE, in ADD COLUMN and in MODIFY — `SET DEFAULT 0` became `DROP DEFAULT` — because the code tested the default with truthiness (`if column.default_value:`). Fixed: every default test is now `is not None`. (12) Indexes lost their definition: CREATE INDEX emitted only the column list, so a partial index (`WHERE active`), an expression index (`lower(email)`) and a GIN index all came out as plain btree indexes on the same columns, and a dropped index came back as one too. Fixed: one shared `_index_create_sql` (UNIQUE, USING method, expression instead of columns, WHERE predicate) used by the add step and by the drop step's rollback. (13) Constraints were unnamed and undroppable: CREATE TABLE emitted an unnamed PRIMARY KEY, unnamed FOREIGN KEYs and inline UNIQUE/CHECK on the column line, and ADD COLUMN emitted inline UNIQUE/CHECK/REFERENCES — an inline UNIQUE is unnamed, so a later DROP CONSTRAINT by the conventional name fails, and the create-then-modify round trip broke. Fixed: every constraint is named (`pk_table`, `fk_table_column`, `uq_table_column`, `ck_table_column`); a column's unique/FK/check are emitted as separate ADD_CONSTRAINT steps (a FOREIGN_KEY branch was added to `_add_constraint_step`); CREATE TABLE and the DROP COLUMN / DROP_OLD_COLUMN rollbacks use the same names. (14) The zero-downtime temp column carried the target's full definition: a NOT NULL column without a default fails on a populated table before the copy step ever runs — the round-2 fix for the temp column was itself the bug. Fixed: the temp column is type-only and nullable; the target's NOT NULL, default and named constraints are applied by a new APPLY_CONSTRAINTS step after the rename, and only when the target actually needs something applied (a plain type change has no step 5). (15) The zero-downtime plan had no backfill check: the COPY step had no validation query at all. Fixed: COPY_COLUMN_DATA carries a backfill query that must return 0 before the contract phase (`WHERE temp IS NULL` for a NOT NULL target, `WHERE temp IS NULL AND old IS NOT NULL` otherwise); the plan's warning now says so, while dual-write and cutover remain application coordination. (16) The plan's hashes were not real: the source hash was the md5 of the *changes* dict and the target hash was the empty string, so a PASS could be carried from one schema pair to another. Fixed: `generate_migration` takes the two schema dicts and hashes each with SHA-256; `main()` and the tests pass them. (17) Reversibility was unlabelled and the DROP TABLE rollback was a comment (`-- Recreate table t (implementation needed)`). Fixed: the DROP TABLE rollback is the real CREATE TABLE (named constraints, plus the table's indexes); every step carries a `reversibility` field (`schema` = the rollback restores the schema exactly; `schema-only` = it restores the structure but NOT the data); DROP COLUMN, DROP TABLE and DROP_OLD_COLUMN are `schema-only`; the summary gains `backup_required` and `data_loss_steps`; the text format prints the backup warning; `--validate-only` now emits a `COLUMN_EXISTS_BEFORE_DROP` check for a dropped column and a `TABLE_EXISTS_BEFORE_DROP` check for a dropped table. Three existing tests were rewritten because their old assertions encoded the defects (reported plainly in the round-3 report): `test_zero_downtime_drop_is_high_risk_and_temp_column_is_complete` (asserted the temp column carries the full target definition), `test_add_column_keeps_constraints` (asserted the constraints inline in the ADD COLUMN), and the integration `test_add_column_with_check_and_fk_executes` (now executes the ADD COLUMN steps on SQLite and asserts the Postgres-only ADD_CONSTRAINT steps by string — live enforcement of an added column's CHECK/FK is no longer testable on SQLite). The round-3 fixes are covered by `test_migration_generator.py` (16 new tests, 33 total) and `test_migration_integration.py` (5 tests).

- **Fourth review round (2026-11-06, also from external reviews):** (18) Table creation followed set-iteration order, so books could be created before authors and PostgreSQL rejected the FK — and SQLite could not see it (it lets CREATE TABLE name a FK to a table that does not exist yet, and FK enforcement is DML-only). Fixed: creation runs in FK dependency order (Kahn's algorithm, alphabetical tie-break); drops run in reverse order; a foreign-key cycle's FKs are deferred to post-create ADD CONSTRAINT steps; MigrationStep.dependencies is now populated (it was never set); every set iteration in the comparator is sorted, so the order no longer depends on the hash seed. (19) compare_schemas() appended without resetting, so a second compare on the same instance duplicated every change, and loading a different schema pair crashed with KeyError in _compare_indexes on the stale tables_added. Fixed: compare_schemas() rebuilds its changes from scratch on every call. (20) The generator's output had never executed on PostgreSQL (only SQLite). Fixed: test_postgres_migration.py (4 tests on real PostgreSQL 16: the FK-order chain, an invalid insert that must fail, a FK cycle that must execute, and a rollback that must restore schema and data) plus a postgres-migration CI job (postgres:16 service). Verified locally on PostgreSQL 16.15: 4 passed; the old generator fails the chain test under PYTHONHASHSEED=1, which is the proof the SQLite tests could not give. The round-4 fixes are covered by test_migration_generator.py (7 new tests, 40 total) and test_postgres_migration.py (4 tests).
- **Dialect (declared, 2026-11-06; also in the module docstring and SKILL.md §3 since round 4):** the generator emits PostgreSQL-style SQL (`ALTER COLUMN ... TYPE`, `ADD/DROP CONSTRAINT`, `information_schema` validation queries). SQLite executes the overlapping subset (CREATE TABLE, ADD/DROP COLUMN, CREATE/DROP INDEX, RENAME TABLE, DROP TABLE), which is what the integration tests cover. Two SQLite gaps, found while writing those tests: SQLite rejects `ALTER TABLE ... ADD COLUMN ... UNIQUE` ("Cannot add a UNIQUE column" — for SQLite that needs a CREATE UNIQUE INDEX instead), and the `validation_sql` on each step uses `information_schema` (PostgreSQL), not SQLite's PRAGMA. The integration tests use PRAGMA as the SQLite equivalent.
- **Tool limitations found by the audit and the eval (not hidden):** (1) the `--format sql` output prints forward steps only — the rollback SQL exists only in the `--format json` output; the skill's rule that every migration needs a reversible counterpart must be satisfied from the JSON output or by hand. (2) ~~The generated SQL does not add a FOREIGN KEY constraint~~ — FIXED (see the fixes above). (3) ~~The `DROP_OLD_COLUMN` step inside the zero-downtime dance is marked LOW risk~~ — FIXED (it is HIGH now). (4) ~~`--validate-only` emits no validation queries for a `DROP COLUMN` step~~ — FIXED in the third review round (it now emits `COLUMN_EXISTS_BEFORE_DROP`, and `TABLE_EXISTS_BEFORE_DROP` for a dropped table). (5) The rollback for a dropped column re-adds an empty column — it does not restore the data. Now labelled, not hidden: such steps carry `reversibility: "schema-only"` and the plan summary lists them under `backup_required` / `data_loss_steps`. The skill's own rules (take a logical backup before dropping a column with data; test the down migration in staging) must be applied by the agent, not relied on from the tool.

- **Fifth review round (2026-11-06, also from external reviews):** (21) Table creation ignored dependencies on changes to existing tables: a new table events with an FK to users.external_id — a column added in the same migration — was created with the FK inline, before the column and its unique existed, so PostgreSQL rejected the migration at the first step (UndefinedColumn; and even column-first it fails without the unique: InvalidForeignKey). Fixed: an FK to a column (or unique) this migration adds is deferred to a late-FK phase after column addition, constraint addition and column modification; the same deferral applies to a new column's own FK (in the column phase and in the zero-downtime follow-up, where the FK action used to live inside APPLY_COLUMN_CONSTRAINTS). An FK to a column that already exists with its unique stays inline. (22) The rollback test only proved PostgreSQL transactional rollback (conn.rollback()), never the generated sql_rollback. Fixed: a new test executes the generated rollback SQL in rollback_order after a commit and compares the schema snapshot before and after; the old test's docstring now says what it proves. The PostgreSQL fixture now drops every table in TABLES and rolls back before cleanup, so a failed test cannot leak tables into the next one. The round-5 fixes are covered by test_migration_generator.py (4 new tests, 44 total) and test_postgres_migration.py (2 new tests, 6 total).
