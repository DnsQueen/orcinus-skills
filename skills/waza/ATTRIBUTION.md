- **A defect in the upstream skill, found by a real run and recorded here:** the skill's inline "Evaluation Spec Format" example writes `expected: "Expected behavior"` (a string) and `validators:` on the task. v0.40.0 rejects that: `cannot unmarshal !!str into models.TaskExpectation`. The correct task format is `inputs.prompt` + `expected: {output_contains: [...], outcomes: [...], behavior: {...}}` + `graders:`. The runnable suite shipped in this repo, `evals/waza-orcinus-verify/`, uses the correct schema — follow it, not the skill's simplified example.
- **References that are not in ORCINUS:** the description says token counting or budget checks should use "waza tokens" — that sibling skill is not bundled here; token counting is not covered by this skill. The skill also mentions the Copilot SDK executor; only the mock executor was proven in this environment (no Copilot CLI/auth here). The tool itself states the limit: `config.executor: mock checks only the harness, not agent quality`.
- **What the mock proves, and what it does not:** the mock executor returns `Mock response for: <prompt>` — it echoes the prompt. So an `output_contains` check passes when the prompt itself contains the expected string (the matching is case-insensitive). A mock run proves the suite parses, the tasks execute, the graders score, the results JSON is well-formed, and the gate can fail (a control task with an absent string fails, and `waza run` exits 1). It does NOT prove the skill being evaluated works. Real grading needs a real executor (`copilot-sdk`) and a real agent run.
- **Evals:** the repo's own eval is `evals/evidence-eval-01.md` — a real run of the Waza CLI (init, run, compare, exit codes) against the shipped suite `evals/waza-orcinus-verify/`.
